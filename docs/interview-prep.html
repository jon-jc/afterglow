Prepare these three · 60–90 seconds each

Problem → decision → trade-off → evidence

1. One financial effect despite repeated delivery

Problem: a worker may commit settlement and crash before acknowledging. A partner may also send several event IDs for the same play.

Decision: guard settlement with the reservation state and commit spend, reservation changes and audit together. Duplicate events can be observed without another financial effect.

Trade-off: correctness depends on durable state and a trustworthy reservation identity. “Exactly-once effect per reservation” is more precise than “exactly-once delivery.”

Evidence: Live proof shows two events for one reservation, one settlement and one duplicate. The lost-acknowledgement tests exercise redelivery after commit.

2. An honest HTTP acceptance boundary

Problem: separately saving a receipt and publishing to a broker creates a crash gap.

Decision: save the receipt and an outbox row in one SQL transaction. Return 202 after that commit. A dispatcher delivers the saved work later.

Trade-off: the outbox needs monitoring, retries and cleanup. Publishing may repeat; consumers still need idempotency. A 202 response means durable acceptance, not settlement.

Evidence: pause/resume smoke checks verify accepted work survives processing interruption. Partial batch responses distinguish accepted items from invalid neighbors.

3. Budget correctness under concurrent requests

Problem: two API instances can read the same available balance and both reserve it.

Decision: serialize allocation on the campaign row, use a conditional update, and enforce the balance constraint in SQL. Store money as integer micros; playback receipts cannot set prices.

Trade-off: a popular campaign can become a lock-contention point. Measure before redesigning allocation into partitions, because that changes the correctness problem.

Evidence: PostgreSQL concurrency tests check the cap. The invariant to explain is spent + reserved ≤ budget, not merely that the HTTP requests returned successful responses.

A little about Fluxgate

“Fluxgate accepts metric points through an HTTP ingestion service, sends them through Pub/Sub, aggregates them into event-time windows, and exposes the stored rollups through a query service. The central concern is producing correct aggregates despite redelivery and late data.”

Its README describes three services, PostgreSQL rollups, a per-window delivery ledger, bounded metric labels and trace propagation across the broker. Use the repository’s architecture and decision records to refresh your own explanation. Fluxgate README and decision records.

From your supplied project description: ingestion waits for Pub/Sub acknowledgement before returning 202; the delivery ledger and rollup commit together; batches report partial success; route-pattern labels avoid unbounded metric cardinality.

Likely follow-up questions

Why Go?

Discuss typed contracts, explicit errors, contexts for cancellation and deadlines, and straightforward HTTP/database tooling. Goroutines make concurrent work convenient, but work still needs bounds. Explain where concurrency is actually useful rather than saying “Go is fast.”

What runs locally versus on GCP?

This demo uses Go, persistent SQLite and a SQL-backed local transport. The repository also contains a PostgreSQL path, Google Pub/Sub adapter, Cloud Run infrastructure and telemetry support. Local SDK/test-server checks do not prove real cloud IAM, dead-letter policy or operational readiness. No cloud deployment is claimed.

How do you classify failures?

Retry transient failures with bounds and backoff. Preserve permanently invalid evidence in quarantine. Replay revalidates the evidence; it cannot turn schema v99 into schema v1. A corrected event needs a new identity. Separate transport dead-lettering from application recovery decisions.

What would you monitor?

Oldest undispatched work, retry/exhaustion rates, settlement lag, quarantine reasons, transaction latency and budget discrepancies. Use bounded labels; put individual IDs in logs/traces. These are the operating signals to discuss, not a claim that every production alert is already deployed.

What would you do before production?

Agree on the partner identity and evidence contract; validate managed Pub/Sub and SQL in staging; test load, backup restoration, migrations and credential rotation; define service objectives and ownership. Real playback authentication, vendor certification and the full campaign lifecycle remain work.

Ownership and teamwork: use a real story

A useful project-review example is the reservation price becoming locked after a definite API rejection: explain how distinguishing rejection from an unknown response preserves retry safety without trapping the user. Present it as review of this demo, not an invented team incident.
