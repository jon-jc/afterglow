Before you share your screen

  1. Double-click Start Afterglow.cmd in the project folder. It builds if needed, starts the local app and opens the browser. A fresh start requires Go 1.27+. Existing saved data stays in place.
  2. Open Afterglow → Overview. Confirm the engine is connected. If updates are paused, resume them.
  3. In Failure lab, ensure workers are not paused and let previous work finish. Do not run fault scenarios concurrently with the main proof.
  4. Return to Overview. Keep just the product tab visible when presenting. These study files are local documents, not product pages.

Each Live proof uses two $0.01 synthetic reservations. Existing records and totals persist, so demonstrate the current run’s evidence rather than expecting an empty ledger. Do not clear the database for the interview.

0:00–0:40 · Overview

1. Explain the problem before clicking

“Afterglow explores playback reconciliation for digital outdoor advertising. Budget is reserved before a play; incoming playback evidence then determines whether that reservation can settle. I wanted to make duplicates, invalid evidence and recovery visible.”

Point out: synthetic data and the local runtime. “This screen runs the actual Go API and worker against a local database. It is not a live advertising platform.”

Explain the balances: reserved means money held for an expected play; settled means accepted evidence consumed that reservation. A duplicate must not move money again.

0:40–2:20 · Overview → Run live proof

2. Run the evidence-backed workflow

Click Run live proof on Overview. The proof opens and runs inline; it should keep you on Overview. The separate Live proof navigation page is optional.

“This run uses two reservations. It deliberately mixes valid events, a duplicate, unsupported evidence and a malformed item. The point is to verify the resulting records, not just show a green HTTP response.”

Either of A’s two events may settle first. Do not predict event ordering. Total settlement for this run is $0.02, not necessarily the amount displayed in global dashboard totals.

2:20–3:15 · Inspect proof evidence

3. Open one receipt

Use the completed proof’s receipt inspection control. Show the event identity, reservation link, decision and original payload. Export the run’s evidence if asked.

“An event ID deduplicates an exact retry. The reservation ID protects the business effect even if a partner sends a different event ID for the same play. Those are two different kinds of duplication.”

Point to the contract: 202 means receipt plus dispatch intent committed in SQL. Settlement is asynchronous. A receipt that settled while dispatch acknowledgement is still pending is not evidence of a second charge.

Evidence scope: proof inspection reads exact IDs. The general ledger shows a recent bounded snapshot, so old proof records need not remain in that list. The exported JSON is observed operational evidence, not a signed audit certificate.

3:15–4:15 · Campaign assurance

4. Connect reliability to operations

Open Campaign assurance, select the campaign used in the proof, and inspect its report. Compare reserved and settled balances, delivery decisions and per-screen breakdowns. Export only after that campaign’s report finishes loading.

“The operational question is whether accepted playback evidence and reserved money reconcile, and which exceptions need attention. This report uses retained campaign history rather than treating the last page of receipts as the whole campaign.”

Totals may include earlier demonstrations. Do not call this audience measurement, reach, conversion attribution or advertising ROI.

4:15–5:00 · Close and invite questions

5. State the boundary and pause

“The local run demonstrates the transaction and retry behavior. There is also a PostgreSQL and Pub/Sub path, but a real rollout still needs partner contract validation, cloud staging tests, operational ownership and load and restore evidence. Which part would be most relevant to your team?”

If you only have two minutes: give the opening, run the inline proof, show one duplicate and the two-cent result, then ask for questions. Save Failure lab for a requested deeper discussion.

  1. Open Partner intake.
  2. Choose an example scenario. Start with Partial success.
  3. Leave Reservation price · USD at $0.01 for rehearsal.
  4. Click Load example. This reserves synthetic budget and fills the editable JSON. It does not send the receipts.
  5. Click Send batch. Inspect the HTTP status and individual item results.

Current behavior: the example field allows $0.01–$1,000.00. The suggested $10.00 demo cap has not been implemented. Use small amounts: changing price creates a new hold, while older holds stay reserved until settled or released after expiry and the receipt grace period. Same-price repeated loads reuse the unsent hold.

Choosing a different scenario or typing a price does not rewrite the current request. Click Load example to apply it. Price is recorded on the reservation, not supplied by the playback receipt.

Optional Failure lab: one fault at a time

Crash after commit

Wait for an empty queue, run the scenario, inspect redelivery/attempts and unchanged spend. Explain: acknowledging before commit risks lost work; acknowledging afterward requires duplicate-safe processing.

Unsupported schema

Inspect quarantine and the preserved payload. Replaying unchanged invalid evidence should fail validation again. Correction is a new event, not an override switch.

These controls affect the local demo pipeline. Do not run them while demonstrating Live proof or another scenario. Return the worker to normal processing afterward.

If something stalls

Live proof is waiting

Check engine connectivity and whether Failure lab paused the worker. Resume processing, then resume the same proof. It saves the run plan in this tab’s session storage so the original identities can be retried. Do not repeatedly start new runs to hide a failure.

Load example reports a rejected reservation

Lower the price and load again. A definite rejection unlocks the field. An unknown response keeps the price locked until retry resolves the original request, which prevents accidental duplicate holds. Expired recovered holds require a fresh load.

The ledger does not match the proof totals

Check campaign filters and time scope. The ledger is a recent snapshot; the dashboard includes previous runs. Use the current proof’s exact receipt inspection, or the campaign report, for the matching scope.

The app is unavailable or showing old code

Use Stop Afterglow.cmd, then Start Afterglow.cmd to rebuild and restart. Reload the browser. This preserves the database. If another app owns port 8090, follow the launcher’s conflict message rather than killing an unknown process.

Asked whether CI is green

Say the recorded local Go, API and browser checks passed. Hosted Actions could not start because of the GitHub account billing/spending restriction. Do not describe blocked jobs as passing.

Your rehearsal checklist

  • I can explain the difference between accepted, settled, duplicate and quarantined.
  • I can explain the difference between event identity and reservation identity.
  • I know what 202 means here, and why it differs from Fluxgate’s broker acknowledgement boundary.
  • I can identify what runs locally and what still needs cloud verification.
  • I can stop after five minutes and let Stanford direct the discussion.
