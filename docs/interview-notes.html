01 / THE OPENING CONVERSATION

The story to remember.

Fluxgate asks: “Can I trust this aggregate when events arrive late or more than once?”
Afterglow asks: “Can I trust this delivery decision when messages repeat and campaign money is involved?”

Your strongest connection to this role is the ability to reason about asynchronous systems: what success means, where state becomes durable, what happens after a crash, and how an engineer investigates the result.

“Tell me a little about yourself.”

SAY IT NATURALLY / ABOUT 45 SECONDS

“My recent backend work has focused on Go, APIs and event-driven systems. One project is Fluxgate, a telemetry pipeline built around Pub/Sub and PostgreSQL. I’ve spent time thinking through problems like duplicate delivery, late data and what an API can honestly promise when it returns success.

“To explore the advertising side of this role, I built a second demo called Afterglow. It takes those reliability ideas into campaign budget reservations and playback reconciliation. What interests me about this team is the combination of integration work, strong engineering fundamentals and learning from engineers who operate these systems in practice.”

CONNECT THE WORK TO THE BUSINESS

“The public CCO and Vistar material helped me understand how much has to line up between campaign booking, ad serving and proof of play. That is interesting backend work: separate systems need a shared understanding of what happened, even when delivery is delayed or repeated. I wanted to build a small example around that boundary and learn how your team handles it at real scale.”

How to keep the conversation clear

  1. Start with the failure: “A retry could count the same event twice.”
  2. Explain the decision: “The result and deduplication record commit together.”
  3. Give the trade-off: “That adds database coordination.”
  4. Offer evidence: “I can show the crash case or the concurrency test.”

Give the short version, then pause. “Would it be useful if I went into the transaction boundary?” is more effective than launching into every component.

02 / THE PROGRESSION

What Afterglow improves—and what it changes.

Afterglow is a separate application, not a new version of Fluxgate. The improvement is applying the same reliability principles to a concrete business workflow, with durable request identities, budget constraints and an operator-visible recovery path.

Dimension Fluxgate Afterglow
Business purpose Turn metric points into trustworthy time-window summaries. Turn playback evidence into trustworthy reservation and spend decisions.
Durable acceptance The ingest API waits for the Pub/Sub publish acknowledgement. The API commits a receipt and dispatch intent to SQL.
Correctness identity A batch’s contribution to a particular window. A tenant-scoped receipt identity plus the reservation’s state.
Important constraint Broker redelivery must not inflate aggregates. A reservation must not settle twice; reserved + spent must stay within budget.
HTTP retry scope The inspected request-idempotency cache is in-memory and per-process. Reservation keys and receipt identities are stored under SQL uniqueness constraints.
Time Event-time windows and a lateness allowance. A valid playback window plus a separate receipt grace period.
Operating the system Telemetry, traces, metrics and query results. Those engineering concepts plus inspectable decisions, held money and replay controls.
THE BRIDGE / ABOUT 30 SECONDS

“Fluxgate taught me to make durability and duplicate handling explicit. In Afterglow I applied that to a finite budget: acceptance, playback evidence and settlement are different steps. I moved the request identities into SQL, added a reservation state machine, and made failures visible in an operations console. The important improvement is being able to explain why a business effect happened once, even if the messages did not.”

The subtle distinction: three different kinds of “duplicate”
  1. An HTTP retry: a client repeats a request after an ambiguous timeout. A durable request key can identify it across API instances.
  2. A broker redelivery: the broker sends the same logical work again because it did not observe an acknowledgement. A consumer ledger/state transition protects the committed effect.
  3. A semantic duplicate: a partner uses a new event ID for a play it already reported. Only a business identity, such as the reservation, reveals that it describes the same effect.

Do not assume protection at one layer automatically solves the others. Fluxgate’s per-window ledger protects contributions under the batch identity it receives; it is not proof that every new batch containing similar points will be recognized as the same client operation.

A good trade-off to acknowledge: Afterglow’s durable HTTP identity requires database availability at the API edge. Fluxgate’s ingest service can remain independent of the aggregation database. The architectures optimize different boundaries.

03 / EXPLAIN FLUXGATE

A pipeline that makes uncertainty explicit.

THE 60-SECOND VERSION

“Fluxgate receives metric points over HTTP, publishes accepted work to Pub/Sub, aggregates the points into event-time windows and serves those rollups through a separate query API. The services can scale around different workloads.

“The main design concern is correctness under failure. The ingest response waits for the broker’s acknowledgement. The consumer only acknowledges after its database work is durable, and the aggregate and its delivery record commit in the same transaction. That makes redelivery safe for an already recorded batch/window contribution.”

Four decisions worth being able to defend

1. A response means something durable happened

If the API replies while data exists only in a process buffer, a crash can lose something the client believes was accepted. Waiting for the publish acknowledgement puts the success boundary at the broker. The cost is publisher latency and dependency availability.

2. Deduplicate at the unit of committed work

A batch may contribute to more than one time window. The ledger records (batch, window), so committing the first window does not falsely mark the entire batch complete.

3. Use event time for the result

A measurement belongs to the period when it happened, not simply when a worker saw it. A watermark and lateness allowance determine when windows can be emitted, balancing freshness with tolerance for out-of-order arrival.

4. Keep expensive reads away from ingestion

The query service is separate from ingest and aggregation. A slow dashboard query should not occupy the same execution path needed to receive telemetry. Separate roles also support narrower permissions.

Walk through the two-window crash example

Suppose batch B contains a point at 10:00:59 and another at 10:01:01. It affects two one-minute windows. The first window commits; the second write fails.

  • A ledger containing only “B processed” would incorrectly suppress the unfinished second contribution.
  • A ledger with (B, 10:00) and (B, 10:01) can distinguish the committed contribution from the missing one.
  • On redelivery, the committed part is skipped and the unfinished part remains eligible to be applied.

The general lesson: the deduplication key must match the transaction’s actual unit of work.

Why the rollup and ledger must share one transaction

If the rollup commits first and the ledger write fails, a retry could add the contribution again. If the ledger commits first and the rollup fails, the retry could skip work that never landed. One transaction removes both partial states.

Failure point Durable state Retry behavior
Before commit Neither change is committed. Apply the contribution.
After commit, before acknowledgement Rollup and ledger both exist. Recognize the recorded contribution and avoid adding it again.

This is an application-level effect guarantee under its identity and retention assumptions. It does not make the network deliver every message exactly once.

Watermarks, late data and idle sources—in plain English

A watermark is a moving estimate of how far event time has progressed. Holding it behind the highest observed event allows some late arrivals before a window is emitted. More allowance means more tolerance and slower visibility.

A source that stops sending may never advance its final watermark. Fluxgate describes a bounded processing-time fallback after a period of silence so the last open window does not remain stranded. That is a deliberate exception to discuss when explaining replay and idle behavior.

Example: a 10:00 measurement arriving at 10:01 should still be reasoned about as a 10:00 measurement. Whether it can still affect that window depends on the configured late-data policy—not on wishful thinking.

Backpressure, rate limiting, partial success and observability
  • Backpressure: publisher flow control sheds excess load rather than building an unbounded queue of waiting requests. A circuit breaker avoids repeatedly waiting on a clearly failing dependency.
  • Rate limiting: charging in points rather than requests reflects the real amount of ingestion work. One request with 1,000 points should not be treated like one request with one point.
  • Partial batches: callers receive accepted/rejected counts and point-specific validation errors. They must inspect the result; HTTP 202 does not mean every point was accepted.
  • Observability: traces carry context across the broker, structured logs help correlate work, and bounded route labels prevent arbitrary URLs from producing unlimited metric series.
  • Read API: bounded ranges and series limits prevent one query from asking the database to reconstruct an unmanageable result. A truncated response is explicitly identified.

Be ready to name a limitation. The inspected Fluxgate HTTP idempotency store is process-local and time-limited. A retry routed to another instance is outside that cache’s guarantee. Also, “stateless service” does not mean “no memory”: the aggregator holds open windows, while durable recovery depends on the broker and database.

Source: Fluxgate idempotency implementation. This is distinct from the durable aggregation delivery ledger.

04 / EXPLAIN AFTERGLOW

A reservation is a promise about money.

THE 60-SECOND VERSION

“Afterglow models the boundary between a reserved ad play and a confirmed playback. The API holds budget for a campaign and screen. Later, a partner receipt is stored together with an outbox record, so accepted work survives a restart.

“A worker checks the receipt’s version, screen, time and reservation. It settles the reservation and updates spend in one transaction with the audit decision. Duplicate receipts do not produce a second charge. Invalid evidence goes to a visible recovery surface instead of disappearing into logs.”

Reservehold campaign budget
→
Accept receiptSQL receipt + outbox
→
Dispatchlocal queue or Pub/Sub
→
Reconcilevalidate business evidence
→
Settle / quarantinedecision + audit

The invariant comes before the components

available = budget − reserved − spent
reserved ≥ 0
spent ≥ 0
reserved + spent ≤ budget

Example: a campaign has $100. A $2 reservation changes available to $98, reserved to $2, and spent stays $0. A valid proof moves that $2 from reserved to spent. A second proof changes none of those balances.

The system stores integer USD micros: one dollar is 1,000,000 micros. The price comes from the immutable reservation, not from the receipt. That avoids floating-point arithmetic and prevents a playback message from choosing its own settlement amount.

1. Durable acceptance through an outbox

Updating SQL and publishing to a broker are two independent writes. Afterglow first commits the receipt and the intent to dispatch it in a single SQL transaction. A separate dispatcher delivers the work later.

Where the crash happens What remains Why recovery works
Before receipt/outbox commit No accepted transaction. The caller can retry using the same event identity.
After commit, before publish A durable pending outbox row. A dispatcher can claim it later.
After publish, before recording dispatch The broker may have the work, and the outbox may retry it. The consumer must tolerate duplicate delivery.
After settlement commit, before ack A settled reservation and persisted decision. Redelivery cannot repeat the same financial effect.

What 202 means here: SQL has committed the receipt and outbox—not that Pub/Sub has it, and not that it has been billed. This differs deliberately from Fluxgate’s broker-acknowledged acceptance.

2. A state machine protects the business effect

held ── valid playback evidence ──→ settled
held ── expiry + receipt grace ──→ released

settled + another receipt → duplicate; no new charge
released + late evidence → quarantine; no automatic charge

The worker checks the supported schema, play duration, timestamp, screen and reservation ownership. The reservation transition, budget movement, receipt outcome and audit entry commit together. A failing audit write therefore rolls back the charge too.

Why event deduplication alone would not be enough

Imagine events A and B both describe reservation R. A unique event ID constraint admits both because their IDs differ. After A settles R, the reservation’s terminal state makes B a duplicate business effect.

That guarantee depends on R being the correct identity for the play. If a real partner accidentally creates two different reservations for the same actual playback, a further partner/business reconciliation rule is needed. The demo does not claim to solve identity mistakes it cannot observe.

3. The budget cap lives in the database

In PostgreSQL, the campaign update obtains a row lock before allocation is decided. A conditional update checks that the available amount is sufficient, and a database constraint enforces the cap independently. A Go mutex alone would only coordinate goroutines inside one process.

TESTED Eighty concurrent $10 reservation attempts against a $250 campaign admit exactly 25. The core test suite passed against real PostgreSQL with Go’s race detector enabled.

The cost: a popular campaign can become a lock-contention hotspot. That is an intentional correctness choice for this demo. Partitioning budget would require a new allocation protocol and carefully defined overspend behavior.

4. Recovery has a clear owner

  • Leases: a dispatcher temporarily owns work. If it disappears, the lease can expire.
  • Fencing: an owner token prevents an old dispatcher from overwriting a newer claim.
  • Transient failures: dispatch retries use backoff and jitter; retry exhaustion is visible.
  • Permanent evidence problems: preserve the receipt and a reason, then quarantine it.
  • Replay: requeue the original payload. Validation and financial protection still apply.
A review finding worth explaining: replay racing with completion

An operator can requeue a quarantined receipt just as an older worker is finishing. If that old worker blindly marks the outbox “done,” it can erase the new dispatch intent.

Afterglow’s completion path takes the delivery lock, checks its current status and follows the same delivery-before-outbox lock order as replay. If replay has returned it to accepted, completion leaves its dispatch intent intact.

How to discuss this honestly: explain it as a code-review and concurrency reasoning example. Do not turn it into an invented production incident or a story about teammates who were not involved.

Release safety is now an explicit boundary

Protected startup requires PostgreSQL, an explicit tenant and API credentials. Schema changes run through a separate migration command; application startup only checks the recorded version and checksum. Tests include a read-only PostgreSQL connection, so the runtime does not need DDL permissions to verify its schema.

Credential rotation can temporarily accept current and previous keys; removing the previous key ends the overlap. These controls improve deployment safety, but real rollout, restore, load and managed-service failure drills still need to happen. See the production release gates.

5. Evidence must be visible

The console reads actual database state: held budget, settled spend, receipt decisions, attempt counts and audit history. Its overview map is synthetic screen inventory. It does not estimate real reach, identify viewers or claim advertising conversion lift.

Production boundary: the easy local launch uses SQLite and a SQL-backed transport. PostgreSQL tests and a real Google SDK test against pstest were run separately. Terraform validated, but managed GCP operation and Vistar certification were not exercised. Neither a race-detector pass nor a successful demo proves a production throughput or availability target.

EXTENSION / PARTNER INTEGRATION

Make the integration contract observable.

Fluxgate asks when telemetry is durable and how redelivery avoids double counting. Afterglow applies those fundamentals to playback reconciliation: settle reserved budget only once.

THE 30-SECOND EXPLANATION

“The partner intake console sends real batches to my Go API. Each receipt gets its own transaction and explicit result. A malformed neighbor cannot erase valid work. Retrying an unchanged event returns its durable identity, while a separate reservation guard prevents another charge from a different event reporting the same play.”

Open Partner intake, choose a scenario, and load an example. It includes one valid receipt, a second event for the same play, and one malformed item. A 207 response exposes partial success. Resubmit unchanged to demonstrate persistent request deduplication; inspect the ledger to distinguish durable acceptance from the eventual financial decision.

The API limits batches to 50 receipts and charges admission tokens per item. Honor Retry-After on 429. Transport failures can have an unknown outcome, so retain the exact event IDs and payload. A 409 means an existing identity was reused with different content.

This is a synthetic contract, not Vistar's wire format or a certified integration. Local transport is SQL-backed; managed Pub/Sub and actual partner contract validation still require staging evidence.

05 / YOUR LIVE DEMO

Four minutes. Three failures. One clear lesson.

Ask whether Stanford would like a brief demo. Start from the overview and keep the explanation focused on the decision being protected. Open Afterglow in another tab ↗

  1. Orient the viewer — 20 seconds

    “These are synthetic campaigns and screens. The numbers come from the running backend. This local mode lets me show the reliability behavior without depending on a cloud account.”

  2. Simulate traffic — 40 seconds

    “The API reserves budget and accepts receipts. The worker then decides whether each play can settle. Accepted and settled are deliberately different states.”

    A clean 12-receipt scenario adds $19.95 of settled spend. Existing data makes the overall total higher.
  3. Send duplicate receipts — 50 seconds

    “Here are five distinct event IDs for one reservation. One should settle and four should be suppressed. I am protecting the financial effect, not just the message ID.”

    That scenario adds one $1.25 charge. Point to the duplicate count and ledger.
  4. Lose an acknowledgement — 60 seconds

    “The next receipt commits and then loses its acknowledgement. The retry is expected. The test is whether the committed balance changes a second time.”

    Run with an empty queue. Inspect attempts and spend; do not claim the injected failure kills an OS process.
  5. Inspect a schema exception — 40 seconds

    “An unsupported version is durable evidence that I cannot safely interpret. It is quarantined with a reason. Replaying it does not make the schema valid.”

  6. Close with the trade-off — 30 seconds

    “The harder production work is agreeing on identity and timing contracts with the partner, then measuring the operating limits. I’d be interested in which of these boundaries your team owns.”

If the demo does not work during the interview

Stay calm: “This is why I separated the business invariant from the UI. Let me show the transaction and its test instead.” Use the README screenshot and test names. Do not repeatedly click a mutation button or claim a stale screenshot is live.

If the worker is paused, resume it. If a campaign is at its cap, explain the rejection. Persistent data is intentional; use a fresh database filename before the interview if you want a clean run.

06 / TECHNICAL FOLLOW-UPS

Short answers you can expand.

“Is this exactly once?”

“The transport can deliver more than once. I aim for one committed business effect under a stable identity, using transactions and deduplication/state constraints. I would be specific about the identity, retention policy and database assumptions rather than describe the whole distributed system as exactly once.”

“Why Go?”

“It fits small network services well: explicit errors, contexts for cancellation and deadlines, straightforward concurrency and a simple compiled deployment artifact. The important discipline is bounding goroutines and in-flight work; concurrency by itself does not make an overloaded dependency faster.”

Point to bounded Pub/Sub receive settings, dispatch deadlines and the database pool. Explain that the local dispatcher is intentionally serial, while PostgreSQL leases support independent dispatchers.

“Why PostgreSQL instead of Redis or just an in-memory map?”

“The balances, reservation state and delivery decision need to agree after a crash. PostgreSQL gives me transactions, constraints and shared coordination between processes. An in-memory map cannot preserve those guarantees across restarts; adding Redis would require reasoning about another consistency boundary.”

For Fluxgate, PostgreSQL also makes ledger and aggregate updates transactional. A purpose-built time-series database could improve other workloads, but the choice should be driven by measured needs and the correctness contract.

“How do you distinguish retryable and permanent failures?”

“A temporary database or transport failure can succeed later. An unsupported schema will not become interpretable merely because I retry it. I retry transient dependencies with bounds; for permanent evidence problems I preserve the payload and reason for review.”

In Afterglow, application quarantine differs from the managed Pub/Sub transport dead-letter subscription. SQL may be unavailable during a sustained consumer failure, so not every transport failure can immediately appear in the console.

“What happens if a valid receipt arrives late?”

“I separate event time from arrival time. The play must fall inside its reservation window, and funds remain held through an additional receipt grace period. After the hold has been released, I quarantine late evidence rather than silently spend money that might already have been reallocated.”

The actual grace period and commercial remedy would be agreed with the business and integration partner. The demo’s 15-minute window plus 15-minute grace is a policy choice, not a statement of CCO’s policy.

“How would you scale this?”

“I would first measure database lock wait, backlog age, transaction latency, connection pressure and delivery throughput. The first likely pressure point in Afterglow is contention on a hot campaign. I would not split budget ownership until I had a clear allocation protocol and evidence that the simpler model was insufficient.”

For Fluxgate, ingestion rate and aggregation cardinality stress different components. Scaling consumers in and out can also create rework when in-memory windows have not committed yet.

“What is specific to GCP here?”

“The Go adapter uses Pub/Sub publish acknowledgement and pull subscription APIs. The deployment template separates API and worker identities, defines dead-letter permissions and keeps CPU available for background processing. Persistent state belongs in Cloud SQL rather than a Cloud Run container’s local disk.”

The Pub/Sub service agent needs the relevant source-subscription and dead-letter-topic permissions for forwarding. Valid infrastructure syntax is only the start; IAM behavior and managed-service failure recovery still need deployment verification.

“How would you approach the real Vistar integration?”

“First I’d clarify the integration type and the team’s ownership boundary. Then I’d agree on identity, time semantics, schema evolution, authentication, retry behavior and reconciliation. I’d implement the vendor contract behind an adapter, use their staging process, test failure cases with them and work through certification.”

Vistar’s public guide describes a proof-of-play URL in the ad response. Afterglow’s JSON receipt is a deliberately synthetic contract. It is a way to demonstrate integration reasoning, not evidence that the application already speaks Vistar’s production API.

“What would you change before production?”

“I’d prioritize a real partner contract and trustworthy playback evidence, then operational controls: complete campaign/catalog lifecycle, migration rollout rehearsals, credential rotation, retention, alerting, backup restore drills and load testing against agreed targets. I’d also review database permissions and fleet-wide admission control.”

The present audit is append-only by application convention, not tamper-proof. The limiter and dispatcher cooldown are per-process. These are specific next steps, not features to imply already exist.

“What do the tests actually prove?”

“They exercise specific invariants: no budget overspend under concurrent requests, one settlement for duplicate evidence, rollback if the audit fails, recovery after database reopen, lease fencing and safe replay. An end-to-end test verifies exact balances through the HTTP and worker flow. Those results do not prove a production SLO or eliminate the need for a real partner integration test.”

The Go race detector finds unsynchronized memory access in exercised code. Transaction tests are what check the business result under database concurrency. Those are complementary checks.

10 / PLAIN-ENGLISH GLOSSARY

The words behind the architecture.

Idempotency
Repeating the same operation does not repeat its intended effect, within a defined identity and retention contract.
At-least-once delivery
Delivery may repeat while the broker works toward acknowledgement. Consumers must tolerate that repetition.
Transactional outbox
Save the business record and the intent to send a message in one database transaction; deliver the message later.
Atomic transaction
A set of changes commits together or none of it commits. There is no durable halfway state.
Invariant
A rule that must remain true, such as reserved plus spent never exceeding a budget.
Lease and fencing token
Temporary ownership of work, plus an identifier that lets storage reject writes from a superseded owner.
Backpressure
A way to limit or reject incoming work when downstream capacity is exhausted.
Jitter
Random variation in retry delays so many clients do not all retry at the same instant.
Watermark
An estimate of event-time progress used to decide which time windows can be emitted.
Dead-letter queue
A separate destination for messages that cannot be processed through the normal delivery path.
Proof of play
Evidence that an ad was displayed. By itself, it does not prove how many people saw it or that it caused a purchase.
Cardinality
The number of distinct values or combinations in a metric’s labels. Too many can overwhelm storage and queries.
